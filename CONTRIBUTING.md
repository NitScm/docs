# Contributing to the nit documentation

The user documentation site: Astro + Starlight, everything in Markdown under
`src/content/docs/`.

Reporting a **security issue**? See [SECURITY.md](SECURITY.md) — for a
documentation site that mostly means *documentation that tells people to do
something unsafe*, which is a real and welcome report.

Participation is governed by the [Code of Conduct](CODE_OF_CONDUCT.md).

## Everything is in English

Pages, commit messages, issues. Translations are welcome as a future structure,
but the source of truth is English.

## Getting set up

```sh
./dev.sh                  # http://localhost:4321
./dev.sh --port 5000      # any astro dev flag is passed through
pnpm run build            # static site into dist/
```

`dev.sh` selects the Node version from `.nvmrc` through nvm, installing it if
missing, and runs `pnpm install` when the lockfile is newer than `node_modules`.

## The rule that matters most

**Do not document behaviour you have not run.**

These pages are read by people deciding whether to put nit in their commit path.
A flag that does not exist, a setting spelled differently from the code, or an
output that never appears is worse than a gap — it costs the reader's trust in
everything around it.

So:

- Check a flag against `nit/cmd/` before writing it down.
- Check a setting against `nit/internal/bootstrap/` — the file key *and* the
  environment variable.
- Check an error code against `nit/pkg/protocol/common.go` and the server's
  handlers.
- **Paste real output.** Run the command and copy what it printed. Several pages
  were corrected because invented output turned out to be subtly wrong: a count
  that did not match what the policy actually withheld, a denial that named a
  rule where the real one named none.
- If you cannot verify something, write what you *did* verify and say plainly
  what is unverified. The docs make that distinction elsewhere — the scaling
  page opens by saying its numbers are derived and not measured — and they
  should keep making it.

## Adding a page

1. Write the Markdown under the right directory.
2. Add its slug to the sidebar in `astro.config.mjs`.

The sidebar is hand-written rather than autogenerated, deliberately: reading
order matters, and alphabetical order would bury *filtered projections* — the
idea everything else rests on — behind *Architecture*.

A slug in the sidebar with no file fails the build, which is the behaviour you
want.

## Structure

| | |
| --- | --- |
| `start/` | What nit does, installing, a first workspace, a first policy |
| `concepts/` | Filtered projections, authorization, guards, push and pull, architecture, glossary |
| `guides/` | Policy bundles, server, workers, forges, console, operations, production, a worked example |
| `reference/` | `nit`, `nitctl`, configuration settings, the HTTP API, error codes |

**Concepts explain why. Guides explain how. Reference is exhaustive and dull.**
A page that mixes the three serves none of them. If a guide is growing an
exhaustive table of flags, that table belongs in `reference/`.

## Links and the base path

The site is served from `https://nitscm.github.io/docs/`, so every URL
carries a `/docs` prefix. **Write links without it** — `[x](/concepts/guards/)`
— and a rehype plugin in `astro.config.mjs` adds it at build time. The base is
declared once, in that file.

The exception is `index.mdx`: Starlight component props and YAML frontmatter are
outside the Markdown pipeline, so its cards use `import.meta.env.BASE_URL` and
its hero actions use relative paths. Follow what is already there.

The dev server applies the base as well, so locally the site is at
**http://localhost:4321/docs/** — the bare origin is a 404, and so is the link
Astro prints when it starts. `./dev.sh` prints the working URL.

That friction is deliberate. Dropping the base in development would remove it
and would make development stop reflecting production, which is exactly how 28
broken links once shipped with a passing build.

## Before you open a pull request

```sh
pnpm run build
```

The build fails on a sidebar slug with no page. Links are not checked
automatically yet — check that a page you linked to exists, and that an anchor
you linked to is a real heading.

## Style

- Prose, not bullet soup. A paragraph that explains a trade-off is worth more
  than five fragments that assert one.
- Say why a thing is the way it is when it is surprising. Readers forgive
  constraints they understand.
- Code blocks are copy-pasteable and complete. A snippet with `...` in the
  middle of a YAML file is not a snippet.
- Starlight asides (`:::note`, `:::caution`, `:::danger`) for things that bite.
  Sparingly — a page of asides has no emphasis left.
- British or American spelling, consistently within a page.

## When the code changes

`reference/` has pages for every flag, setting and error code. If you change one
in `nit/`, change it here in the same pull request. The reference pages exist
to be trusted; a stale one is a bug.

The engineering documents in `nit/docs/` — `ARCHITECTURE.md`, `PROTOCOL.md`,
`POLICY.md`, `CONFIGURATION.md`, `VALIDATION.md`, `SCALING.md`, `DECISIONS.md` —
remain the authority on internals and on *why* each decision was made. These
pages are for people integrating nit, not for people modifying it.

## Good first contributions

- A page where the wording is clearer to someone who has not read the code.
- A missing cross-link between a concept and the guide that uses it.
- An example that does not run.
- Anything in `reference/` that does not match the current code — those are the
  highest-value fixes here.
